Overview

프로젝트 개요

Piece는 온보딩부터 가치관 기반 매칭·탐색까지 이어지는 소개팅 서비스의 Android 클라이언트로, Google Play에 출시되어 지금도 실사용자가 쓰고 있는 앱입니다.

사용자는 질문에 답하며 프로필을 등록하고, 조건에 맞는 상대를 탐색·매칭합니다. 매칭 이후에는 인앱 스토어에서 재화를 구매해 추가 기능을 이용하거나 친구 초대로 리워드를 받을 수 있고, 알림·설정 화면에서 앱 사용 환경을 관리할 수 있습니다.

Case Study 01

인앱 결제 유실 방지

지급은 됐는데 정산은 누락되는 구조적 문제를 찾고, 고친 과정

Problem — 지급과 소비 처리(consume)가 분리되어 있던 구조

기존 결제 흐름은 클라이언트가 Google Play 구매 후 서버 API를 호출해 재화를 지급받고, 그 응답이 성공적으로 돌아오면 클라이언트가 다시 Google Play에 소비 처리(consume)를 요청하는 구조였습니다. 이 구조에서는 서버 API 통신이 중간에 끊기면 재화는 이미 지급됐는데 소비 처리는 누락되는 상황이 생길 수 있었고, Google Play는 일정 기간 내 소비 처리되지 않은 구매를 자동으로 환불 처리하기 때문에 유료 아이템은 지급된 채로 매출만 환불되는 이중 손실로 이어질 수 있는 구조였습니다.

Solution — 지급·소비 처리를 서버 한 번의 트랜잭션으로 결합 + 재조회 안전망

구매 지급과 소비 처리를 클라이언트-서버 왕복 두 단계로 나누지 않고, 서버가 구매 검증 API를 처리하는 시점에 Google Play Developer API를 통해 지급과 소비 처리까지 함께 확정하도록 구조를 바꿨습니다. 클라이언트는 검증 API 하나만 호출하면 되고, 네트워크 상태와 무관하게 지급과 소비 처리가 항상 함께 성공하거나 함께 실패하도록 만들어 유실 가능성 자체를 없앴습니다.

PieceApi.kt — 검증과 지급을 한 번에 처리하는 단일 엔드포인트

// 서버가 이 호출 한 번으로 구매 검증 + 재화 지급 + Google Play 소비 처리까지 확정
@POST("/api/payments/in-app")
suspend fun verifyPurchaseProduct(
    @Body verifyPurchaseProductRequest: VerifyPurchaseProductRequest
): ApiResponse<VerifyPurchaseProductResponse>

추가로 앱의 메인(매칭) 화면에 진입할 때마다 아직 처리되지 않은 구매 건이 있는지 Google Play에 다시 조회해 서버로 재전송하는 방어 로직을 넣어, 혹시 놓친 케이스가 있어도 다음 진입 시 자동으로 복구되도록 안전망을 마련했습니다.

BillingHelperImpl.kt — 미처리 구매 재조회 방어 로직

override suspend fun checkUnprocessedPurchases() {
    connectGooglePlayIfNeeded()

    // 아직 승인 처리되지 않은 구매 건만 필터링
    val purchases = queryPurchases().filter {
        it.purchaseState == Purchase.PurchaseState.PURCHASED && !it.isAcknowledged
    }
    if (purchases.isEmpty()) return

    val totalReward = supervisorScope {
        purchases.map { purchase ->
            async { runCatching { fetchPurchaseReward(purchase, null) }.getOrDefault(0) }
        }.awaitAll().sum()
    }

    if (totalReward > 0) _purchaseResult.send(PurchaseResult.Success(totalReward))
}

이 로직은 매칭 메인 화면 진입 로직(fetchMatchInfo()) 안에서 매번 자동으로 호출되도록 연결해, 사용자가 앱을 다시 열 때마다 결제 정합성이 자동으로 점검되게 만들었습니다.

Case Study 02

회원가입 이탈 방지

Amplitude 데이터로 문제를 찾고, 로컬 저장으로 풀어낸 과정

Problem — Amplitude 회원가입 퍼널 분석 (최근 30일)

단계화면유저 수이탈률
1약관 동의90명-
2권한 요청87명3.3% 이탈
3회피 설정85명2.3% 이탈
4가입 완료85명0% 이탈

전체 전환율 94.4% (이탈률 5.6%)

Amplitude 퍼널 분석 결과, 전체 사용자 흐름 중 회원가입 단계의 이탈률이 가장 높다는 것을 확인했습니다. 특히 약관 동의 이후 권한 요청 단계로 넘어갈 때 이탈이 두드러졌고, 한 번 이탈한 사용자는 처음부터 다시 입력해야 한다는 부담 때문에 재가입을 포기할 가능성이 높다고 판단했습니다.

Solution — 입력 데이터 로컬 자동 저장 + 재접속 시 이어쓰기

프로필 등록 중 입력하는 닉네임·생년월일·지역·가치관 답변 등을 Proto DataStore에 실시간(디바운스 500ms)으로 자동 저장하도록 구현했습니다. 재접속 시에는 저장된 데이터가 있는지 먼저 확인해 등록 화면으로 자동 진입시키고, 입력해 두었던 값을 그대로 복원해 처음부터 다시 작성하지 않아도 되게 만들었습니다.

RegisterProfileViewModel.kt — 입력값 디바운스 자동 저장

// 입력 상태가 바뀔 때마다 500ms 디바운스 후 로컬에 자동 저장
private fun observeAndSaveDraft() = viewModelScope.launch {
    state
        .drop(1)
        .map { it.toRegisterProfileData() }
        .distinctUntilChanged()
        .debounce(500.milliseconds)
        .collect { draft ->
            val userId = currentUserId ?: return@collect
            profileRepository.saveRegisterState(userId, draft)
        }
}

MainViewModel.kt — 재접속 시 저장된 데이터 여부로 자동 라우팅

when (userInfo.userRole) {
    REGISTER -> {
        // 저장된 등록 데이터가 있으면 등록 화면으로, 없으면 처음 가입 화면으로
        val hasSavedState = profileRepository.getRegisterState(userInfo.userId) != null
        if (hasSavedState) ProfileGraph.RegisterProfileRoute
        else AuthGraph.SignUpRoute
    }
    else -> MatchingGraph.MatchingRoute
}

가입을 완료하면 clearRegisterState로 저장된 draft를 즉시 삭제해, 다음 가입자의 데이터와 섞이지 않도록 처리했습니다.

Case Study 03

인앱 로그 Drawer

Logcat 없이도 QA 현장에서 바로 원인을 확인할 수 있게 만든 관리자 전용 도구

Problem — QA 이슈마다 개발자가 기기를 직접 붙잡고 Logcat을 봐야 했던 문제

QA 중 이슈가 발견될 때마다 개발자가 해당 기기를 직접 건네받아 Logcat을 붙여서 원인을 확인해야 했습니다. 어떤 유저의 계정이었는지, 어떤 API가 실패했는지, Amplitude 이벤트가 제대로 찍혔는지를 그 자리에서 바로 알 수 있는 방법이 없어 매번 기기와 케이블, 개발 환경이 갖춰진 자리로 돌아가야 했고, 그때마다 QA 흐름이 끊겼습니다.

Solution — 좌측 엣지 스와이프로 여는 관리자 전용 로그 Drawer

화면 좌측 끝에서 당기면 열리는 관리자 전용 로그 Drawer를 구현했습니다. User ID·Device ID를 바로 복사할 수 있고, API 호출 내역과 Amplitude 이벤트를 앱 안에서 그대로 확인할 수 있어 서버를 거치지 않고도 QA 현장에서 바로 원인 파악이 가능해졌습니다.

release 빌드에서도 안전하게 — 배포 버전에서는 아무나 이 Drawer를 열 수 없어야 하므로, Firebase Remote Config로 내려주는 userId·deviceId 허용 목록에 포함된 경우에만 열리도록 했고, debug·qa 빌드에서는 항상 노출해 개발 중에는 자유롭게 확인할 수 있게 했습니다.

DebugDrawer.kt — release 빌드에서의 관리자 판별 게이트

// release 빌드에서는 원격 설정으로 승인된 유저·기기만 Drawer 노출
if (isRelease() && !isDebugAdmin) {
    content()
} else {
    ModalNavigationDrawer(
        drawerState = drawerState,
        drawerContent = { /* User ID, Device ID, Amplitude 로그, API 로그 */ },
        content = content,
    )
}

API 로그 — OkHttp Interceptor에서 모든 요청·응답을 가로채 메서드·경로·상태코드·응답 바디를 메모리에 최대 200건까지 저장하도록 구현했습니다.

NetworkLogInterceptor.kt — 요청/응답 가로채서 로컬에 저장

class NetworkLogInterceptor @Inject constructor(
    private val networkLogHelper: NetworkLogHelper,
) : Interceptor {
    override fun intercept(chain: Interceptor.Chain): Response {
        val request = chain.request()
        val response = chain.proceed(request)

        networkLogHelper.log(
            ApiLog(
                timestamp = System.currentTimeMillis(),
                method = request.method,
                url = request.url.encodedPath,
                statusCode = response.code,
                responseBody = response.peekBody(MAX_BODY_BYTES).string(),
                isSuccess = response.isSuccessful,
            )
        )
        return response
    }
}

Amplitude 로그 — 관리자 모드에서는 이벤트를 실제 Amplitude로 전송하는 대신 로컬 스트림에 쌓이도록 라우팅해, 운영 지표를 오염시키지 않으면서도 화면 전환·클릭 등 이벤트가 의도대로 찍히는지 개발자가 바로 눈으로 확인할 수 있게 했습니다.

AdminAwareAnalyticsHelper.kt — 어드민 모드에서 이벤트를 로컬로 라우팅

class AdminAwareAnalyticsHelper(
    private val amplitudeHelper: AnalyticsHelper,
    private val debugHelper: AnalyticsHelper,
) : AnalyticsHelper() {
    @Volatile private var isAdminMode = false

    override fun setAdminMode(isAdmin: Boolean) { isAdminMode = isAdmin }

    override fun logEvent(event: AnalyticsEvent) {
        if (isAdminMode) debugHelper.logEvent(event) else amplitudeHelper.logEvent(event)
    }
}
